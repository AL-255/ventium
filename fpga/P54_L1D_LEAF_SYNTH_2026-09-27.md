clock. Source `rtl/mem/ven_l1d.sv` SHA-256:
`99f001307df6b604f459c1f615b26e9e114d075af9c03592b2798d2db47f6d84`.

limit. Artifacts are under `/tmp/p54-l1d-synth-{packed,banked,paired}-r3/`.
The code-buffer and code-stream rows use the later source SHA-256
`5a74539a1732538401dc1b086a8d94a51c62f90a1842e231cf6754c61b94d33b`
and `/tmp/p54-l1d-synth-{code-buffer,code-stream}-r6/`; their extra logic is
guarded by the corresponding defines, so the preceding three configurations
are unaffected. Both later rows were synthesized from this exact source.

The banked single-port layout saves **1,187 LUTs (9.9%)** versus packed while
preserving the logical 8 KiB, two-way, 32-byte-line geometry. Its eight 256×32
banks infer Xilinx `RAM256X1D`: 32 primitives per bank, except bank zero uses
64 because the legacy crossing read needs a second async read port. The dual
hit port adds **3,424 LUTs** over banked single-port, principally for lookup,
per-bank address selection and two width/offset data selectors; it has no
integrated throughput benefit yet. These are isolated leaf figures, not the
processor's total utilization.
The one-line code-fill staging buffer adds **56 LUTs and 302 FFs** to banked
L1D. It prevents instruction fills from evicting D-cache lines, but is not a
second architectural I-cache and does not increase the P5 L1 capacity.
Streaming already-arrived code words from that buffer lets the following
instruction-fill beats overlap the rest of the backing burst. The isolated
streaming variant uses **237 fewer LUTs and 11 more FFs** than the non-streaming
code buffer in this synthesis run; synthesis sharing explains why adding a
control path need not increase mapped LUT count. It does not remove the
platform's default line-replay policy.

An earlier `dc_bank[bank][row]` array with dynamic bank writes **failed** RAM
inference (`Synth 8-7186`, 65,536 data registers). That invalid probe was
stopped after diagnosis; its output is not part of the comparison. The current
source uses a separately generated byte-write RAM template per bank. Directed
64/128-set cache, coherence, stream/window, and paired-hit benches pass.

The clock constraint is **45.0 MHz** for every row. The reported WNS is
**not routed Fmax**: the out-of-context probe lacks
top-level clock skew, I/O delays, memory-system fanout and placement. Vivado
warns `HD.CLK_SRC` is unset. Neither an isolated timing pass nor the
single-port area saving proves a full-core 45 MHz implementation. Paired-hit
promotion requires a real dual EA/DTLB/issue/commit integration and a measured
workload improvement large enough to justify its LUT cost. An isolated
synchronous BRAM bank has now been measured below; an integrated BRAM L1D
remains unmeasured and must include read latency and collision semantics.

The later owner-tagged L1/AXI sideband and registered-ACK overlap source
(`ven_l1d.sv` SHA-256 `c1b2500168fd6b6424bcd8416c5b6412c27c2a1bda1b7bb72f9b8526b4fca171`)
was synthesized with the same `paired` OOC recipe at 45 MHz. It uses
**14,819 LUTs** (12,579 logic, 2,240 LUTRAM), **6,251 FFs**, and **zero
BRAMs**; synthesis WNS is **+16.632 ns**, implying an isolated constrained
register-path limit of roughly **179 MHz** (22.222 − 16.632 ns). Reports are
under `/tmp/p54-l1d-paired-overlap-r1/`. The previous paired row is **not a
matched source A/B**, so its 567-LUT difference cannot be attributed solely
to overlap. Neither figure is placed-and-routed core Fmax. The 32-pair
back-to-back microbench proves two resident bank-distinct returns per clock,
but the core's sideband requests remain tied low pending checked D2/DTLB and
retirement ownership; this is not a gameplay IPC gain.

The window-reuse row is a matched rerun of code stream using the same
`ven_l1d.sv` source SHA-256 as the preceding code-buffer/stream rows. Both
variants used single-threaded Vivado 2025.2 synthesis and the same 45.0 MHz
constraint; reports are in `/tmp/p54-l1d-code-stream-reuse-{base,candidate}-r1/`.
Retaining an already captured, tag-checked full line costs **658 LUTs (+6.2%)**
and 3 fewer FFs in this isolated leaf, with no BRAM change. Synthesis WNS is
0.713 ns lower but remains positive at the 45.0 MHz constraint. This is not
routed core maximum frequency. In a separate 22-case fixed-work, matched

families from 4 to 3 clocks per four-instruction loop without an architectural
trace difference; distinct-line loads, stores and frontend straddles did not
improve. The current full-PC profile does **not** enable window reuse, and no
new gameplay IPC result exists. See
`verif/bench/P54_SDECODE_DIRECTED_2026-09-27.md` for the composed microprofile.

## Synchronous dual-port BRAM feasibility (not integrated)

`ven_p54_bram_bank.sv` is an isolated 256×32, byte-write, two-registered-read
macro for one of the eight physical P54 word banks. Its bounded cycle test
(`verif/bench/run-p54-bram-bank.sh`) passes all 256 rows on both read ports,
back-to-back requests and byte-write readback. Vivado 2025.2 synthesized the
source SHA-256 `e383c9b7fe82afbdf0780da0b4cad69e69785d5b404e1159b67c3c85906c763c`
to **one `RAMB36E2`, zero LUTs, zero LUTRAMs and zero external FFs** in
`/tmp/p54-bram-bank-synth-r1/`. Eight such data banks would nominally use
eight RAMB36 tiles, before tags, address/byte selection, arbiter, or any
additional storage. The output registers were absorbed into the BRAM; the
report has **no WNS** because standalone I/O paths are unconstrained. Its
1.960 ns primitive minimum period is not a routed processor Fmax.

This is a resource-feasibility result, **not** a replacement for the current
L1D or a gameplay speedup. An integrated variant must present the row address
one cycle before consumption, preserve the existing registered-hit handshake,
and arbitrate a same-row fill/store write against port-B reads. The macro
deliberately rejects that write/read collision in simulation rather than
depending on vendor-specific read-during-write data. It must pass the full
cache/coherence and two-lane ownership tests before its area can be compared
with the current `RAM256X1D` implementation.

Reproduce the leaf probe, with no other Vivado instance running:

```sh
timeout --signal=TERM --kill-after=15s 540s \
  fpga/run_vivado_exclusive.sh -mode batch \
  -source fpga/synth_p54_bram_bank.tcl \
  -tclargs /tmp/p54-bram-bank-synth-example
```

## Eight-bank dual-read BRAM data-array feasibility (not integrated)

`ven_p54_bram_data.sv` composes eight of the byte-write 256×32 BRAM banks.
It accepts translated, tag-checked U/V dword-read requests to distinct banks
in one cycle and returns separately owned, registered responses on the next
edge. Same-bank U/V requests serialize; a write excludes reads of its bank.
It retains an output-register response under backpressure and blocks a write
that would overwrite the held U response. Flush cancels held owners. These
rules avoid relying on unspecified same-address BRAM read-during-write data.

The bounded microbench (`verif/bench/run-p54-bram-data.sh`) passes **62 checks**:
all 56 ordered distinct-bank pairs, same-bank replay, separate owner/data
returns, held-response stability, independent write versus blocked collision,
consumption and flush cancellation. Vivado 2025.2 synthesized the data-array
source SHA-256
`6b79b1ec66080813775402641f3fe42cf5dde5c46d64aa36545226ea09215e95`
on `xck26-sfvc784-2LV-c` to **8 RAMB36, 212 LUTs, 40 external FFs, zero
LUTRAMs**, with synthesis WNS **+19.847 ns** against a 45 MHz clock. Artifacts:
`/tmp/p54-bram-data-synth-r1/`. No orphan Vivado remained after the run.

The small LUT count is **not** directly comparable to the complete L1D rows
above: this leaf omits tags, valid/LRU, byte extraction, split extents,
cacheability, fill/control FSM, translation, and the real core request path.
Its synchronous BRAM reads require an address one edge ahead of consumption;
the present single-ack L1D cannot be replaced by this module without a
request/response pipeline and collision-safe fill/store integration. The
out-of-context WNS constrains only internal register paths, not external
input/output paths or routed processor Fmax. There is no gameplay IPC result.


## Shared bank-zero crossing read (September 28 opt-in)

`VEN_L1D_BANK0_SHARED_XLINE` makes a crossing dword use bank zero's ordinary
read address for the *next* line, instead of inferring a second asynchronous
read port. A crossing dword consumes bank seven of its first line and bank
zero of the next; first-line bank zero is not needed for that response. The
registered first-line image is incomplete on such a capture, so the existing
full-line window-reuse and FP high-half qualifiers are cleared for that owner.
The option requires `VEN_L1D_BANKED_DATA` and is **not enabled by default**.

Matched Vivado 2025.2 out-of-context runs at a 45 MHz constraint, same source
SHA-256 `7bddab07f48b96206c8e16b20ca4fed521cf76caf047562810258b7b69b38628`:

| Define profile | Total LUTs | LUTRAMs | FFs | BRAMs | Synthesis WNS | Implied constrained leaf register-path frequency |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| code stream + window reuse | 11,305 | 2,240 | 6,399 | 0 | +16.908 ns | ~188 MHz |
| same + shared bank zero | 10,785 | 2,048 | 6,404 | 0 | +17.635 ns | ~218 MHz |

The opt-in saves **520 LUTs**, including **192 LUTRAMs**, while adding five
FFs. The frequency figures are derived only from constrained internal leaf
paths (`1/(22.222 ns - WNS)`), **not** routed core or board frequencies; I/O
paths and whole-system fanout remain unconstrained. Reports are under
`/home/yukidama/ventium-background-sep28.B3cxzoKA/l1d_bank0_{base,shared}/`.
Each synthesis completed inside its nine-minute cap, sequentially under the
exclusive Vivado launcher; no Vivado process remained afterward.

The complete L1D gate passed at both 64 and 128 sets, including the opt-in
crossing/return data, cache coherence, fills and bypass. The gate was rerun
with scratch on a filesystem with free space after an earlier run stopped
while compiling an unrelated configuration on a nearly full scratch volume.
Paired-hit tests passed fresh U/V capture (153
checks), primed U/V capture (171), and two-window ownership (187). A matched
31-case full-core candidate/control microbenchmark showed identical
architectural traces and exact cycles in every case, including a new resident
crossing-read → first-line word-zero → next-line word-zero loop (5.000 cycles
per five-instruction iteration in both builds). This does not establish
no regression for every gameplay access pattern: a crossing capture cannot
be reused as a complete first line, and no candidate gameplay result exists.
